# AI にまとめて話題へ振り分けさせる（Issue [#8](https://github.com/ex-day/poc/issues/8)）

1次解析（`../first_pass.py`・`../first_pass_v2.py`）では、ルールとベクトルだけで投稿を話題に振り分けようとした。わかったことは次の3つ。

- 返信先があれば、まとまりの F は 0.60 くらいになる
- 返信先がないと、F は 0.39 まで落ちる
- AI に回す投稿が 5〜8割になる

Ruri のベクトルでは、話題の始まりと続きを見分けられなかった（AUC 0.41）。

そこで、投稿ごとに AI に回すかを決めるのをやめた。会話の投稿をまとめて AI に渡し、話題に振り分けさせる。

## 中身

| ファイル | 役割 |
|---|---|
| `build_inputs.py` | AI に渡す入力を作る（`data/`。正解とメモは入れない）。返信先あり／なし（全部消す）の2通り、一括と10件ずつ |
| `prompts/split.md` | 振り分けの指示（対象の指示：同じ対象を話題にする。#8） |
| `prompts/split_flow.md` | 振り分けの指示（流れの指示：会話の流れのひとまとまりを話題にする。#14） |
| `results/<提供元>-<モデル>_<呼び方>_<指示>_<返信先>[_<回>]/` | AI の振り分け（会話ごとの JSON）。例：`claude-sonnet_subagent_flow_reply`。提供元は claude／openai など、呼び方は subagent（Claude Code のサブエージェント）／api、指示は object（`split.md`）／flow（`split_flow.md`）、返信先は reply／noreply。同じ条件を複数回回したときは `_r2` などを付ける。`score.py` はこの形のフォルダを全部読む |
| `score.py` | 正解と比べて `results/score.md` を書く（数え方は `../first_pass.py` と同じ） |

## やり方

- 判定役は、正解を見せないサブエージェント（Claude Code のサブエージェント。#12 と同じ）。指示と入力のファイル以外を読まないように指示した。
- 条件：Haiku・Sonnet × 返信先あり・なし × 対象の指示・流れの指示。会話の全投稿を一度に渡す（一括）。各1回。
- 会話：Claude が書いた6本と、人（利明）が書いた3本（`tsurumi_38`・`kohoku_31`・`posts`）。人が書いた会話は `written_by: "human"`。集計は2つに分けて出す。

## 数え方

| 指標 | 意味 |
|---|---|
| まとまりの F | 分けすぎ・混ぜたの両方を数える（B-cubed） |
| 適合 | 別の話題を混ぜない。低いと、あとから分け直せない（重い外れ） |
| 再現 | 同じ話題を分けすぎない。低くても、束ねれば戻せる（軽い外れ） |
| 細分を許す F | AI の話題を、対応する正解の話題ごとに束ねてから数える。細かく分けただけなら下がらず、混ぜたときだけ下がる |
| 厳しい F | 正解を先頭の話題だけにして数えたまとまりの F（「でも可」の話題は当たりにしない）。「でも可」をどちらも当たりにすると、話題をまとめる側が有利になるため、モデルを比べるときに並べて見る |

正解が複数ある投稿（「T3 でも可」など）は、どれに振り分けても当たり。`results/score.md` の3節に、AI がどちらに入れたかを出す。

```bash
cd context/ai_split
python build_inputs.py
# results/<条件>/<会話>.json を作る（サブエージェント、または API で）
python score.py
```

## 結果（#14 途中経過1）

まとまりの F（人が書いた3本 ／ Claude が書いた6本）：

| 条件 | 対象の指示 | 流れの指示 |
|---|---|---|
| Sonnet・返信先あり | 0.77 ／ 0.91 | 0.87 ／ 0.89 |
| Sonnet・返信先なし | 0.77 ／ 0.90 | 0.84 ／ 0.88 |
| Haiku・返信先あり | 0.78 ／ 0.83 | 0.79 ／ 0.85 |
| Haiku・返信先なし | 0.84 ／ 0.90 | 0.87 ／ 0.75 |

- AI は話の中身の種類（飲食店、富士の付く地名など）を軸に分ける。人は場所（駅周辺か、魚河岸通りか）も軸にしている。
- 考察は Issue #14 に残す。

## 結果（#14 途中経過2：OpenAI との比べ）

人が書いた3本、流れの指示。GPT-5.6 Sol は Codex エージェント経由（PR #17。API を直接呼んだものではない）。

| 条件 | まとまりの F | 厳しい F | 話題の数（正解は12） |
|---|---|---|---|
| GPT-5.6 Sol・返信先あり | 0.96 | 0.88 | 8 |
| GPT-5.6 Sol・返信先なし | 0.92 | 0.91 | 10 |
| Claude Sonnet・返信先あり | 0.87 | 0.89 | 10 |
| Claude Sonnet・返信先なし | 0.84 | 0.79 | 10 |

- 返信先ありでは、GPT と Claude Sonnet はほぼ並ぶ（厳しい F）。GPT は「でも可」の話題をまとめるので、今の数え方では高く出る。
- 返信先なしでは、GPT のほうが崩れなかった。
- 鶴見の「駅周辺の店」と「魚河岸通りの店」は、どのモデルも1つにまとめた。
- GPT の返信先なしは、最初は返信先ありと同じセッションで作られ、結果が一字一句同じだった。新しいセッションで取り直すと、結果が変わった。条件ごとに実行を分けないと、前の答えを引き継ぐ。
- 各条件1回だけ。揺れは測っていない。

## 読むときの注意

- **会話と正解は、7本のうち6本を Claude が書いたもの。** posts.json だけは人が書いたもの。判定役も Claude なので、話題の切れ目の感覚が同じで、高めに出ている可能性がある。人が書いた会話や、実際の投稿で確かめる必要がある。
- 流れの指示は、人が書いた会話を見たあとで書いた（例え話は会話と関係ないものにした）。人が書いた会話の結果は高めに出ている可能性がある。
- 区切って順に渡す条件（10件ずつ、前の振り分けを引き継ぐ）も試した。ただ、判定役が「前の結果を書いてから次を読む」手順を守ったか確かめられなかった（道具の呼び出し回数が、手順どおりなら要る回数より少ない）。そのため、結果には入れていない。やり直すときは、10件ずつ、メッセージで順に渡す。
