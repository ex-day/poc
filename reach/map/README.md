# 到達圏を時間の帯の面にして地図に重ねる（Issue [#40](https://github.com/ex-day/poc/issues/40)）

寄り道の画面（[platform#134](https://github.com/ex-day/platform/issues/134)）で、Discovery が少ないうちは検索の結果がまばらになる。そこで、結果のリストより先に「ここから何分でどこまで行けるか」を地図の面で見せる案を、実データで確かめる。

- モックで比べた描き方のうち、駅のまわりの円を合体させた面（blob）を使う
- 時間の帯は 15・30・45・60分。中ほど（早く着く）ほど濃くなるように、外側の帯から重ねる
- 地図は国土地理院の淡色地図（地理院タイル）、描画は MapLibre GL JS
- 場所は2種類に分けて見せる：**声のある発見**（`reach.spot` の `sample`、仮の Discovery）と、**声のない場所**（`wikidata`。まだ誰も話していない場所）

## 面の作り方

1. `reach.reach_from(駅, 分)`：起点の駅から片道で行ける駅と分数（`pgr_drivingDistance`。分数 ＝ 乗り始めの待ち5分 ＋ グラフの所要時間。起点の駅は0分）
   - 同じ名前の駅のグループが近く（1.5km 以内）にまとまっている場合（横浜の JR と市営地下鉄など）は、すべてを起点にする。離れた場所に同じ名前がある（住吉、福島など）ときはエラーにする。`reach.group_nodes`（03）は複数あると必ずエラーにするので、`reach.name_nodes` を別に作った
2. `reach.isochrone_bands(駅)`：帯 B ごとに、B 分より早く着く駅のまわりに半径 `min(B − 着く分, 15) × 80 ÷ 1.3` m の円を作り、`ST_Union` で合体する
   - 80 m/分：歩く速さ（不動産の表示の「1分＝80m」）
   - 15分：駅から歩く時間の上限
   - 1.3：直線の距離に対する道のりの遠回りの比。誤差を「行けない」側に寄せるための割引
3. `reach.spots_in_reach(駅, 分)`：場所ごとに、いちばん早く着く時間（駅に着く分 ＋ 直線の距離 × 1.3 ÷ 80）と、そのときの駅
4. `reach.reach_map_json(駅, 分)`：帯の面・駅・場所を GeoJSON にまとめる（画面はこれを読む）

本物の等時間線ではない。駅のまわりの道のりは測らず、川・線路・海で歩けない側にも円が広がる（#23 の歩きのグラフは使っていない）。地図で見て、それが気になるかどうかも確かめたいことの1つ。

## 動かし方

前提：`reach/README.md` の手順で鉄道のグラフ（01〜03）と、場所（04 と `load_spots.py`）が入っていること。

```bash
cd reach
psql postgresql://postgres:postgres@127.0.0.1:5432/ex_day_poc -f sql/11_isochrone.sql
source ../../../.venv/bin/activate   # worktree の場合。リポジトリの直下なら source ../.venv/bin/activate
python map/server.py                 # http://127.0.0.1:8040/ を開く
```

- 別の DB は `EXDAY_DSN`、別のポートは `--port` で指定する
- `http://127.0.0.1:8040/?from=新横浜&min=30` のように、駅と分を URL で渡せる（寄り道の画面の `/reach/横浜?min=30` の代わり）
- 地図のライブラリ（unpkg）と地理院タイルはネットから読むので、オフラインでは地図が出ない

画面：

- 駅の名前を入れて「寄り道」で読み直す（候補は前方一致で出る）
- スライダーで 15〜60分を切り替える。データは60分ぶんを1回だけ取り、切り替えは画面の側で絞る
- 最初の画角は30分圏までに合わせる。時間を広げても画角は変えない（探す範囲と見せる範囲を分ける。platform#134）
- 駅は薄く小さな点。マウスを乗せると駅名と分数が出る。場所の点を押すと、着く分数と、どの駅から歩くかが出る
- 「一覧」で、声のある発見を先に、近い順に並べる

SQL だけで見る：

```sql
SELECT * FROM reach.reach_from('横浜', 60) ORDER BY t_min;
SELECT band_min, station_count, round((ST_Area(geom::geography) / 1e6)::numeric, 1) AS km2
FROM reach.isochrone_bands('横浜');
SELECT name, source, t_min, via_station, walk_min FROM reach.spots_in_reach('横浜', 60) ORDER BY t_min;
```

## 確かめたいこと

- 実データ（N02 の全駅、Wikidata の数万件）で、面の見え方は blob のモックと同じように読めるか。川や海をまたぐ円が気になるか
- 60分ぶんで帯の面・駅・場所を返す時間（画面に「DB ○ms」と出る）。1回の表示で `reach_from` を3回呼んでいるので、遅ければまとめる
- 返す GeoJSON の大きさ（簡略化は 0.00005度 ≒ 5m）
- 声のある発見が少ないとき（今は sample の数件）、声のない場所の点が「まだ誰も話していない場所」として見えるか。それとも邪魔か
- 起点ごとの差（都心の駅、郊外の駅、新幹線の駅）

## 試した結果

この PR の時点では、実データでは動かしていない（作った側の環境に N02 のデータと Docker がないため）。確かめたのは次だけ：

- PostgreSQL 16・PostGIS 3.4.2・pgRouting 3.6.1 で、作り物の小さなデータ（2路線10駅、場所5件）を入れ、`11_isochrone.sql` の関数がエラーなく動き、分数・帯の面・場所の着く時間が手計算と合うこと
- `server.py` の API（`/api/reach`、存在しない駅のエラー、`/api/stations`）
- ヘッドレスの Chromium で画面が出て、スライダーで帯と件数が切り替わること（地理院タイルは読めない環境だったので、背景の地図は未確認）

実データでの結果は、動かしたあとにここへ書く。
