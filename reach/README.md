# 寄り道できる駅のリストを、粗く出す（Issue [#5](https://github.com/ex-day/poc/issues/5)）

出張の帰りなど、「残り時間のうちに、どこかに寄り道できるか」を出すための最初の実験です。乗換案内を作るのではなく、「近くから○○分くらいで行ける駅」を、時刻表を使わずに粗く出します。詳しい経路は、乗換案内のアプリで調べてもらう前提です。

- 移動時間 ＝ 線路の距離 ÷ 路線ごとの表定速度 ＋ 乗換の時間
- 寄り道できる駅 ＝ 出発駅からの時間 t1 ＋ 滞在時間 ＋ 帰着駅までの時間 t2 ≦ 使える時間
- 誤差は「行けない」側に寄せる（速度は遅め、乗換は多め）。「行けると言われたのに間に合わない」を避けるため

## データ

国土数値情報 鉄道データ（N02）2025年版

- 取得元：https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N02-2025.html
- 出典：「国土数値情報（鉄道データ）」（国土交通省）を加工して作成
- データはリポジトリに入れない。各自ダウンロードし、`UTF-8` フォルダを `load_n02.py` に渡す

中身（確かめたこと）：

| ファイル | 件数 | 中身 |
|---|---|---|
| `N02-25_Station.geojson` | 10,234 | 駅。点ではなく、ホームの範囲の線。路線ごとに1件。駅コードとグループコード（乗換できる駅のまとまり）つき |
| `N02-25_RailroadSection.geojson` | 21,933 | 線路の区間。駅の中と駅の間で区切られている。どの駅とどの駅の間かは持っていない |

- 駅の線は、すべて、同じ路線の区間の1つと同じ形をしている（ホームにあたる区間）
- 区間の端点の97%は、ほかの区間とつながっている
- 新幹線は事業者種別（`N02_002` = 1）で分けられる
- 地下鉄という区分はない。東京メトロは「民営鉄道」、都営・横浜市営などは「公営鉄道」、Osaka Metro の多くは「軌道」。事業者と鉄道区分から振り分けた（`02_build_graph.sql`）
- 新横浜は、東海道新幹線・横浜線・ブルーライン・相鉄・東急の5件が、同じグループコード（004501）だった
- 同じ駅コードの駅が複数件ある場合がある（大阪の東海道線は5件）。今は1件だけを駅として使う

## 試した結果（Ubuntu の PostgreSQL 16・PostGIS 3.4・pgRouting 3.6 で確認）

- 取り込みからグラフ作成まで：数秒。路線 597、点 22,239、乗車の辺 21,933、乗換の辺 1,549、駅 10,154（全駅がホームの辺と対応した）
- Scenario 01（新大阪 → 新横浜、360分、滞在90分）：寄り道できる駅グループが 486。1回の問い合わせに約0.6秒（最初の版は5〜6秒。下の「速さ」）
  - 東海道新幹線の駅（京都、米原、名古屋、浜松、静岡、熱海、小田原など）は、どれも余裕64分で並ぶ。新大阪〜新横浜をまっすぐ行くのと同じ時間で寄れるため
  - 新大阪〜新横浜の移動は約216分（待ちを含む）。のぞみ（約2時間20分）よりかなり遅く、こだまに近い。新幹線を150km/hに置いた分、遅めに出ている
- 京急本線の横浜〜浦賀を30km/hに上書き：横浜〜浦賀の33km分の辺（50本）に当たり、品川〜横浜の23km分は40km/hのまま

## 速さ

最初の版は、1回の問い合わせに5〜6秒かかった。PR #21 のレビュー（Codex）で「開始点が複数あるせいではないか」と指摘を受け、測った。

| 条件（新大阪から、260分まで） | 時間 |
|---|---|
| グラフを読むだけ（探索ほぼなし） | 約0.03秒 |
| 開始点1つ | 約0.4秒 |
| 開始点10（新大阪のホームの両端。最初の版） | 約4.1秒 |

`pgr_drivingDistance` に開始点を複数渡すと、開始点ごとに探索を1回ずつ行う。そこで、仮の点 0 を置き、そこから各開始点へ所要時間 0 の辺を足して、1回だけ探索するようにした（`reach.edges_from`）。結果は最初の版と一致し（486件、t1・t2 とも同じ）、約0.6秒になった。

`equicost := true`（各点を近いほうの開始点に割り当てる）も試したが、3駅で t2 が1分ずれたので使わなかった。

## わかった問題（#7 への引き継ぎ）

- **同じ名前の駅が複数のグループに分かれていると、駅名では指定できない。** 例：東京は 003766（新幹線・東海道線・丸ノ内線など）と 003785（京葉線）に分かれていて、`reach.reachable('新横浜', '東京', …)` はエラーになる（グループコードで指定すれば動く）。全国に同じ名前がある駅（住吉、福島など）も同じ。名前の解決は関数ではなく入力の画面の仕事とし、入力した文字から駅の候補を路線名・都道府県つきで出して選んでもらう前提にする。ex-day では、現在地から近い駅のグループを出すほうが基本になる見込み。関数は、選ばれたグループコードを受け取る
- **長距離の特急がある路線で、寄り道を見逃す。** 例：名古屋から中央線で塩尻・上諏訪を通って新宿へ帰る寄り道（しなの・あずさ）は、在来線を普通列車を含めた一律の速度（40km/h）にしているため出てこない。直すなら、特急を「停車駅にしか点を置かない別の路線」として足し、停車駅の間だけ特急の速度にする案がある（停車駅は手で書く。京阪神の新快速も同じ仕組みで扱える）。#5 では作らない
- 新幹線の速度を1つにすると、のぞみとこだまの差が出ない。停まる駅によって大きく違う
- 在来線の特急・快速も同じ。速達の列車がある路線では、遅めに出る
- 乗換の時間が一律10分。大きな駅（新宿、東京）では足りず、小さな駅では多すぎる
- 終電・最終の新幹線は扱えない
- 同じ駅コードの2件目以降のホームは、駅として使っていない

## やらないこと

- **グループコードが違う、歩いて乗り換えられる駅どうし（例：綱島と新綱島）はつながない。** データの手入れが大変になるうえ、ほしいのは駅ではなく、駅のまわりの施設や Discovery だから。その分、経路は遅めに出る（「行けない側に寄せる」方針の範囲）。正確な乗り継ぎは、乗換案内のアプリに任せる

# 寄り道の提案を組み立てる（Issue [#6](https://github.com/ex-day/poc/issues/6)）

寄り道できる駅のリスト（#5）は、それだけではユーザーへの価値にならない。駅のまわりにある場所と、ユーザーの興味を突き合わせて、「寄り道の提案」にできるかを確かめる。

比べること：

1. **絞り込みの順序**
   - 案1：行ける駅 → 駅のまわりの場所 → 興味で並べる（`reach.suggest_reach_first`）
   - 案2：興味で全国から上位 k 件を探す → そのうち行ける駅のまわりにあるものだけ残す（`reach.suggest_interest_first`）
2. **並べ方**（`compare_suggest.py`）
   - A：興味との近さの順
   - B：近さの上位30件を、遠回りの小さい順に並べ直す
   - C：近さ − 0.05 × 遠回り（時間）の順

## 駅のまわりの範囲（仮）

- 滞在時間の中で、駅から800m（片道10分ほど）までは歩けるものとする
- それより遠い場所は、余分に歩く往復の時間が余裕に収まれば候補にする。半径 ＝ 800m ＋ 分速80m × 余裕 ÷ 2（上限2km）。距離は直線
- 同じ場所に複数の駅から行けるときは、遠回りが小さい駅を使う
- 遠回り ＝ その駅を経由した t1＋t2 − まっすぐ帰る時間。まっすぐ帰る時間は、寄り道できる駅のうち t1＋t2 が最小のもので近似する

## 試した結果

### 仕組みの確認（文字の重なりの基準 `ngram-baseline`。意味は分からない）

クラウドの検証環境（PostgreSQL 16、PostGIS 3.4、pgRouting 3.6、pgvector）で、流れが動くことだけを確かめた。

- 取り込み：40,084件（Wikidata 40,062、サンプル 22）。埋め込みを含めて8秒
- 案1の候補：新大阪 → 新横浜で 3,365件、新横浜 → 東京で 3,582件。1回 2〜5秒（初回が遅い）
- 案2：1回 0.8〜0.9秒

並び順の良し悪しは、Ruri の埋め込みで動かしてから見る。

### Ruri v3 30m での結果（手元、MacBook Pro・mps）

結果の全体は `results/suggest_cl-nagoya_ruri-v3-30m.md`。取り込み（4万件の埋め込みを含む）は数分。

**速さ**：案1は1回 0.7〜1.0秒、案2は 0.3〜0.5秒。どちらも実用の範囲。

**絞り込みの順序**：

- 案2は、k が小さいと取りこぼす。「温泉に入りたい」「湖を見たい」は k=50 で0件、k=200 でも1〜7件。全国で興味に近い場所の多くは、行ける範囲の外にあるため
- k=1000 にすると、どの条件・興味でも、案1の上位10件をすべて含んだ
- 行ける範囲の計算は約0.6秒で、場所の件数に関係なく一定。案1で取りこぼしがなく、速さの差も小さいので、**案1（行ける駅 → 駅のまわり → 興味で並べる）を基本にする**。案2は、場所が桁違いに増えて、駅のまわりの候補が多すぎるときに考える

**並べ方**：

- A（近さだけ）は、遠回りが大きく余裕が1〜9分しか残らない場所が上に来る（二条御所：遠回り28分・余裕9分、旧徳川昭武庭園：遠回り95分・余裕5分）。寄り道としては危うい
- B・C は、帰り道の途中で降りるだけの場所が上に来る。Scenario 01 の「城を見たい」で小田原城（遠回り0分・余裕64分）、「温泉に入りたい」で熱海の温泉寺（遠回り1分・余裕61分）。「寄り道」の感覚に近い
- 近さの値が 0.78〜0.87 に固まっていて、差が小さい。B の「上位30件」のような区切りは、興味によって効き方が変わる。C（近さ − 遠回り）のほうが扱いやすい
- 余裕がほとんど残らない場所は、並べ方より前に外したほうがよい（例：余裕15分未満は出さない）

**中身の質**：

- **中身の濃いサンプルの Discovery が強い。** 「港町の歴史を知りたい」は象の鼻パーク・元町商店街・汽車道・横浜開港資料館、「魚料理を食べたい」は深川めし・生麦の食文化が上位に来た。どちらも、名前だけでなく、Subject やわかってきたこと（説・価値）を文章に含んでいる
- **Wikidata の場所は、名前と短い説明しかなく、外れが多い。** 「城を見たい」に京都市市民防災センターや豊橋市防災ひろば、「湖を見たい」「温泉に入りたい」「庭園を散歩したい」に世界一小さな公園が出る。名前の雰囲気で近くなっている
- **「湖を見たい」に湖が1件も出ない。** Wikidata の湖は点（湖の中ほど）で入っていて、駅から2km以内に入らない。湖・川・散歩道のように広がりのある場所は、点ではなく範囲（Area・Route）で持ち、範囲の端までの距離で測る必要がある
- 「温泉に入りたい」「魚料理を食べたい」は、そもそも温泉の施設や飲食店がデータにないので、応えられない（予想どおり）
- 小田原城が「港町の歴史を知りたい」の上位に来るなど、サンプルの Discovery でも外れはある

### わかったこと

- 寄り道の提案は、仕組みとしては作れる。行ける範囲の計算は速く、場所の件数に左右されない
- **提案の質を決めるのは、行ける範囲の計算ではなく、Discovery の中身。** 名前だけの場所では興味と結び付かず、Subject やわかってきたこと（説・価値）を持つ Discovery は興味とよく結び付いた
- 場所の持ち方（点か、範囲か）で、提案に出るかどうかが変わる
- 並べ方は、遠回りを入れたほうが「寄り道」らしくなる。余裕の少なすぎる場所は先に外す

### F02 への影響

- 寄り道の提案で興味と結び付くのは、Discovery が持つ「何が体験できるか、何がわかっているか」の文章だった。F02 が会話から取り出すわかってきたこと（とくに価値）は、そのまま提案の材料になる
- F02 で取り出す価値は、「誰が言ったか」より「そこで何ができるか・何が感じられるか」が分かる書き方であるほど、提案に使いやすい
- 場所の種別（点・範囲・経路）を、見立ての段階から持っておくと、提案の距離の測り方に使える
